# LiteServer 优化评估报告

| 项 | 内容 |
|---|---|
| 评估日期 | 2026-10-24 |
| 方法 | 微基准量化分配与延迟 + 端到端压测交叉验证 + 并发正确性测试 |
| 环境 | macOS arm64 / .NET 10.0.5 / JIT 与 NativeAOT 双构建 |

## 已实施并验证

### 1. 路由匹配零分配（主要收益）

**问题** 每个请求的路由匹配都会分配内存：

| 路径类型 | 优化前延迟 | 优化前分配 |
|---|---|---|
| 精准命中 | 0.112 µs | 72 B/op |
| 通配命中 | 0.386 µs | **392 B/op** |
| 未命中 | 0.143 µs | 192 B/op |

三个来源：
- `RouteMatch` 是 `sealed class` → 每次返回都堆分配（72 B）
- 通配匹配用 `string.Split` → 数组 + 子串（192 B）
- `TryMatchInList` 每次 `lock (list) list.ToArray()` → 复制路由表

**改法**
1. `RouteMatch` 改为 `readonly struct`（值类型不分配）
2. 通配切段改用 `stackalloc Span<Range>` + `ReadOnlySpan<char>` 比较，彻底去掉 `Split`
3. 路由表从「可变 `List` + 读时加锁复制」改为「**不可变数组快照**」：
   注册期加锁整体替换引用，读取期零锁零复制
4. `NormalizePath` 增加快路径：已规范化的路径直接返回原引用

**结果**

| 路径类型 | 优化后延迟 | 优化后分配 |
|---|---|---|
| 精准命中 | **0.048 µs**（2.3× 更快） | **0 B/op** |
| 通配命中 | **0.255 µs**（1.5× 更快） | **0 B/op** |
| 未命中 | 0.139 µs | **0 B/op** |

端到端验证（无中间件的最小服务，同负载交叉对照）：

```
优化前  33.2k / 34.7k / 36.6k req/s   → 中位数 34.7k
优化后  43.1k / 47.4k / 49.7k req/s   → 中位数 47.4k
提升约 37%
```

> 注意：在带完整中间件的示例服务上，这个收益被 socket I/O 与其它开销掩盖，
> 端到端差异在噪声范围内（±5%）。分配减少的真实价值在于**降低 GC 压力**：
> 高 QPS 下每请求少 72–392 B，一小时可减少数十 GB 分配。

### 2. 中间件管线无锁化

原先每次 `InvokeAsync` 都 `lock (_lock) _middlewares.ToArray()`。
改为 volatile 不可变数组引用，读取期零锁零分配。逻辑等价，注册期仍加锁。

### 3. 并发正确性验证

无锁读取必须证明安全。测试：4 个线程持续注册路由的同时，1 个线程持续匹配。

```
3 秒并发读写: reads=31,930,387  hits=31,930,387  errors=0  routes=1,246,888
✓ 无异常，稳定路由始终命中
```

3193 万次并发读、124 万次并发写，零异常、零漏命中。

## 已评估但未实施

按「收益 / 风险 / 工作量」排序，列出可继续做的方向。

### A. 值得做（收益明确、风险低）

| 项 | 现状 | 建议 | 预期收益 |
|---|---|---|---|
| **响应头写入** | 每个响应多次 `Headers[key] = value`，`NameValueCollection` 内部会做大小写不敏感查找 | 常用头（Content-Type/Content-Length）走 `ContentType`/`ContentLength64` 属性而非 `Headers` | 微基准另有 24 B/次 的比较器开销，可省 |
| **`GetQuery` 大小写兜底** | 缺键时会遍历 `AllKeys` 线性查找 | 若确认请求来自标准客户端，可去掉兜底或改用预建字典 | 少一次全表扫描 |
| **静态文件 FileStream 复用** | 每请求 `new FileStream` + `open` 系统调用 | 引入小型文件内容缓存（需带 mtime 校验） | 小文件场景可提升 2–3×，但**必须解决 ETag 陈旧问题**（见下） |

### B. 需要权衡（收益与风险并存）

| 项 | 说明 |
|---|---|
| **WebSocket 广播串行** | `BroadcastAsync` 当前 `foreach + await` 逐个发送。连接数多时首尾延迟叠加。可改为 `Task.WhenAll` 并发发送，但需注意单连接写入不是线程安全的——需为每个连接加发送队列/锁 |
| **`RequestScope` 的 AsyncLocal 开销** | `AsyncLocal<T>` 每次赋值有成本。当前每请求 2 次赋值（设值 + 还原）。可考虑仅在 `ServiceProvider != null` 时才设，已有此逻辑但可再确认 |
| **`IServiceScope` 每请求创建** | 即使处理器不用 DI 也会创建作用域。可加「本请求是否真的解析过服务」的懒创建（lazy scope） |
| **连接表上限** | `_activeConnections` 仅受 `MaxConnections` 限制，无每 IP 限制。可加按 IP 的连接配额 |

### C. 不建议做（实测无收益或风险过高）

| 项 | 原因 |
|---|---|
| **静态文件元数据缓存** | 已实测：端到端无收益（7256 → 7260 req/s），且导致 ETag 陈旧——文件从 4 B 改 11 B 后 ETag 未变，客户端收到 304 持续读旧内容。已回退，见 git 历史 |
| **路由结果缓存（path→RouteEntry 字典）** | 路由匹配现已 0.048 µs 且零分配，加一层缓存反而引入字典查找（约 0.05 µs）与失效管理成本，净收益为负 |
| **`string` 路径改 `Span` 全链路** | 匹配层已用 Span；再往下改意味着公开 API 接受 `ReadOnlySpan<char>`，会破坏现有签名且 AOT 下收益有限 |

### D. 安全与并发方面的进一步加固

| 项 | 现状 | 建议 |
|---|---|---|
| 请求体大小全局限制 | 仅示例的 upload 端点做了限制 | 库层提供 `MaxRequestBodyBytes` 选项，在中间件统一拦截 |
| 慢速攻击防护 | 已实测 Slowloris 不阻塞其它请求 | 可加每连接读超时 |
| 响应头注入 | 已实测无 CRLF 注入 | 保持现状 |
| 路由表变更的可见性 | 无锁快照保证「要么看到旧的完整数组，要么看到新的」 | 已正确，无需改动 |

## 结论

**主要瓶颈不在路由**。路由匹配已优化到 0.048 µs / 0 分配，占单请求总耗时（约 20–40 µs）的比例可忽略。
当前端到端吞吐的限制因素是：

1. **`HttpListener` 自身的 accept 与 socket I/O**（关 keepalive 吞吐腰斩即为证）
2. **静态文件的实际文件系统调用**（`open`/`read`，static 约为 health 的 55%）
3. **JWT 的 HMAC-SHA256 计算**（JWT ≈ health，说明其成本可忽略）

若要进一步提升吞吐，方向应是**减少系统调用**（如文件缓存、`sendfile`）而非优化应用层逻辑。
但每一项都须像本次一样做端到端 A/B 验证——本项目已有一次「微基准看着可观、端到端为零」的前车之鉴。
